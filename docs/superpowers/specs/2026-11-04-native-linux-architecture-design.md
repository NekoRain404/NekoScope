# NekoScope 原生 Linux 架构与需求规格

- 状态：待用户审阅
- 日期：2026-11-04
- 产品：NekoScope
- 范围：面向 Linux 桌面环境的原生硬件信息、实时监控、压力测试、基准测试与报告应用

## 1. 产品目标

NekoScope 为 Linux 用户提供统一、易读且可追溯的硬件信息和健康状态视图。产品综合参考 HWiNFO、AIDA64、Hardinfo2、s-tui 等项目，兼顾硬件信息深度、持续传感器监控和可控的压力/基准测试。

原生正式版必须读取真实系统和硬件数据。H5 原型中的模拟数据只用于原型展示和自动化 UI 测试，不能在真实采集失败时静默填充到原生版。每项数据都应能说明来源、更新时间以及读取状态。

首期目标是覆盖主流桌面 Linux 发行版和常见 x86_64 硬件，并为 ARM64 等架构保留扩展能力。数据覆盖以底层接口实际暴露能力为边界；无法通用读取的字段应清楚标记，而不是承诺所有机器都能提供完全相同的信息。

## 2. 用户与核心场景

- 普通用户快速查看 CPU、内存、GPU、存储、网络、主板和系统概况。
- 高级用户检查设备标识、驱动、拓扑、频率、温度、风扇和 SMART 等细节。
- 用户观察传感器随时间的变化，筛选设备或类别并调整图表显示。
- 用户运行有时长、负载和停止条件的压力测试或基准测试，并查看结果。
- 用户生成可分享的系统报告，同时控制隐私字段是否包含或脱敏。

## 3. 技术架构

### 3.1 主应用

- 语言：C++20。
- UI：Qt 6 Quick / QML。C++ 层拥有采集、数据模型、权限状态、任务生命周期和报告逻辑；QML 层负责页面、交互、主题和可视化。
- 渲染：使用 Qt Quick 场景图与可用的 GPU 加速后端。启动诊断中显示实际使用的渲染后端；支持在驱动有问题时切换到软件渲染，并记录降级状态。
- 构建：CMake，模块边界清晰，硬件探测和任务调度不依赖 UI 生命周期。
- 线程：耗时探测、轮询和外部进程运行在工作线程/异步任务中；UI 线程不执行阻塞式 I/O。

建议模块边界：

1. `core`：领域数据类型、采集接口、能力状态、错误和时间戳。
2. `collectors`：按硬件类别实现的 Linux 数据源适配器。
3. `sensors`：传感器发现、轮询、单位转换、历史缓冲和告警规则。
4. `tests`：压力/基准工作流、外部工具适配、保护条件和结果解析。
5. `reports`：采集快照、隐私策略和 JSON/HTML 导出。
6. `ui`：QML 页面和模型绑定。

### 3.2 Rust 的采用边界

主程序和 Qt/QML 集成以 C++ 为主，避免多语言边界扩大构建、打包和调试成本。只有在调研证明某个独立模块能获得明显的安全性或生态收益时才引入 Rust，例如复杂二进制数据解析或可单独测试的纯计算组件。Rust 模块应通过稳定、窄小的 C ABI 或独立进程接口接入；不得让采集数据模型、对象生命周期或 QML 绑定同时存在两套实现。是否引入 Rust 属于具体模块的设计评审，不作为首期硬性依赖。

## 4. 数据模型和可读性约定

每个展示字段应尽可能携带：

- 值、规范单位和必要时的原始值。
- 数据来源（例如 `/sys` 路径、D-Bus 服务、内核接口或外部库）。
- 采集时间和刷新策略。
- 状态：可用、不可用、不支持、权限不足、设备离线、读取错误或数据过期。
- 适用的设备标识和采集器版本信息。

对单位、基数和精度作一致处理，避免把 MHz/GHz、摄氏/华氏、十进制/二进制容量混用。传感器应保留源值和单位转换规则。未知、不可读和零值必须区分。刷新频率应按数据类型配置，避免高频扫描导致明显功耗或系统负担。

## 5. 硬件信息范围

以下是产品目标范围，不意味着每个设备或发行版都能提供所有字段。

### 5.1 处理器

厂商、型号、架构、微码、插槽/封装、核心与线程数量、在线 CPU、每核拓扑、NUMA 关联、当前/标称频率、频率范围、缓存层级、指令特性、虚拟化能力、内核可见漏洞缓解状态和相关 CPU flags。对动态频率，应区分瞬时频率与标称信息，并注明读取来源。

### 5.2 内存与 NUMA

总量、可用量、已用量、交换空间、内存条/通道和频率（可读取时）、NUMA 节点、HugePages、内存映射信息。SPD、DIMM 序列号、时序等只在平台固件或安全接口允许时提供；权限不足或无接口时显示状态原因。默认不展示序列号。

### 5.3 主板、固件和系统

主板厂商/产品/版本、BIOS/UEFI 厂商/版本/日期、SMBIOS/DMI 能提供的字段、启动模式、内核版本、发行版标识、桌面会话、虚拟化/容器环境、主机架构和启动时长。DMI 字段应按隐私规则处理。

### 5.4 PCI、USB 与其他设备

总线树、设备类别、厂商/产品 ID、子系统 ID、驱动绑定、设备路径、链路能力（可读时）、USB 设备拓扑和连接状态。设备详情应能从总览进入，并能以树形/分类列表浏览。

### 5.5 图形与显示

GPU 型号、PCI 标识、内核驱动、驱动版本（可取得时）、显存和显存使用率（依供应商支持情况）、GPU 利用率、温度、频率、功耗/风扇（接口可用时）。显示器部分包括连接器、分辨率、刷新率、色彩信息及 EDID 可提供字段。供应商专有指标通过可选适配器提供，不作为基础运行依赖。

### 5.6 存储

块设备、型号、容量、总线/传输协议、分区和挂载、文件系统、使用量、只读/可移动状态、NVMe 控制器与命名空间、SMART 健康和温度（设备与权限支持时）。任何可能改变磁盘内容的操作不属于硬件信息采集功能。

### 5.7 网络、音频、电池和电源

网络接口、驱动、链路状态/速度、MAC（默认脱敏）、地址信息（报告默认脱敏）、计数器和 Wi-Fi 连接质量（系统接口允许时）；音频设备及驱动；电池电量、健康、循环计数、功率和电源状态；适配器/电源设备信息（平台暴露时）。

### 5.8 温度、风扇和传感器

显示温度、电压、风扇转速、功耗、电流、频率、利用率等可用指标。传感器标注所属设备、通道、单位、来源、最小/最大值、告警阈值（若来源提供）和更新时间。阈值来源应明确区分硬件提供、系统提供和用户配置。

## 6. Linux 数据源与依赖策略

优先使用稳定、发行版普遍可用的系统接口，并按能力探测，不假设路径或服务一定存在。

| 用途 | 首选来源/项目 | 设计约束 |
| --- | --- | --- |
| 处理器、内存、内核信息 | `/proc`、`/sys`、`sysconf` 等 libc 接口 | 解析器需处理字段缺失、内核差异和容器视图 |
| 设备枚举、热插拔 | `libudev`/udev 数据库、sysfs | 能力探测；不得要求特定桌面环境 |
| 传感器 | hwmon/sysfs、`lm-sensors`/`libsensors` | 不要求用户运行 `sensors-detect`；无驱动时解释不可用 |
| 拓扑/NUMA | sysfs，必要时 `hwloc` | 可选依赖，基础页面不依赖 hwloc 才能运行 |
| 磁盘与挂载 | sysfs、`/proc/self/mountinfo`、UDisks2/D-Bus | UDisks2 不可用时保留可读取的基础设备信息 |
| GPU/显示 | DRM/sysfs、libdrm、libdisplay-info、供应商 API | 可选后端；通用信息优先于专有统计 |
| SMART/NVMe | 系统设备接口及经审查的现有工具/库 | 只读采集；权限和设备支持必须明确呈现 |
| 压力测试 | 可选 `stress-ng` | 单独发现可执行文件和功能版本，不内嵌其源码 |
| CPU/内存基准 | 首期评估 `sysbench` | 结果必须包含工具版本、参数和机器上下文 |
| 磁盘/图形扩展基准 | 可选 `fio`、`glmark2` 等 | 默认不启用破坏性磁盘写入；扩展测试需显式警示和确认 |

`hwinfo/libhd`、Hardinfo2、s-tui、lm-sensors、hwloc、UDisks2、libdrm、libdisplay-info、stress-ng、sysbench、fio、glmark2 和 Phoronix Test Suite 均可作为行为、数据源或适配方式的参考。优先复用稳定 API 和系统组件，不复制已有项目的硬件探测实现。将 `hwinfo` 作为可选采集后端的价值、可移植性和许可证应先评估，不把它设为所有发行版的必需依赖。

对工具型依赖采用运行时能力发现：缺少可选依赖时隐藏对应能力或解释不可用原因，不能导致主应用崩溃。包管理器安装提示可以提供发行版对应的软件包名，但默认不自动修改系统。

## 7. 权限与安全

- 主 GUI 默认由普通用户运行，禁止要求用户以 root 启动整个应用。
- 对可由普通用户读取的数据直接读取。
- 需要授权的操作优先通过已有系统接口（如 Polkit、UDisks2/D-Bus）按操作授权；请求应有明确目的和最小权限。
- 暂无安全、可移植授权通路的数据标记为“需要权限”或“当前系统不支持”，不通过提权子进程偷偷读取。
- 所有采集和测试操作均应可取消；停止后清理子进程和资源。
- 启动第三方工具使用 `QProcess` 参数数组，不拼接 shell 命令。校验路径、参数范围、超时和退出状态，并限制可执行文件发现范围。
- 磁盘基准默认只允许只读模式；写入测试为独立的显式扩展，必须标明目标设备、数据破坏风险和恢复条件。
- 报告默认脱敏序列号、MAC、主机名、用户目录及网络地址等可识别字段，并提供逐类纳入控制。

## 8. 页面和交互

原生应用保留 H5 原型的六个主要入口，并以真实数据替换正式环境中的模拟数据：

1. **概览**：CPU、内存、GPU、存储、温度和系统状态摘要；显示异常、缺失和过期数据。
2. **硬件详情**：按设备类别和设备树浏览细节，支持搜索、复制字段和展开来源/状态信息。
3. **传感器**：实时列表和历史曲线；可按设备、类型筛选，选择图表序列、固定关注项、暂停显示和清除历史。
4. **压力测试**：选择 CPU/内存等负载类型、线程/内存量、持续时间和停止条件；显示负载、温度和风扇变化。
5. **基准测试**：运行受支持的基准并记录可复现参数、工具版本和系统上下文；提供结果历史和比较。
6. **报告**：选择硬件类别/字段，预览脱敏结果，导出 JSON 和可读 HTML。

主题支持明暗模式；用户可调整强调色、图表配色以及曲线可见序列。色彩设置应保证状态不仅依赖颜色表达，并兼顾对比度和色觉差异。传感器与设备过滤、曲线选择采用适合多选的控件，测试模式采用清晰的分段选择和数值输入。

## 9. 压力测试与保护

压力测试系统参考 s-tui 的负载与实时监控体验，后端可调用 `stress-ng`。NekoScope 负责启动、监测、停止、超时和结果记录；测试结束后确认子进程退出，不将外部工具的成功启动等同于测试完成。

- 测试前展示负载类型、预计资源用量、时长和将采集的温度等指标。
- 用户可手动停止；支持最长运行时长和温度阈值停止条件。传感器不可用时，不得声称温度保护已启用。
- 默认提供保守时长和负载；允许用户在 UI 中调整，但限制到可验证范围。
- 系统进入低电量、热状态异常或关键采集失效时，应按配置停止并记录原因。
- 运行时持续展示状态、已用时间、可停止操作和关键传感器；页面导航不得让任务失去控制。
- 外部进程崩溃、被杀或无可解析输出时，记录失败/中止状态，不生成伪造的成功分数。

## 10. 基准、历史与报告

基准结果应包含测试名称、版本、参数、开始/结束时间、硬件上下文、操作系统/内核、退出状态、原始输出摘要和解析后的指标。比较不同机器或不同工具版本时清楚标识条件差异，不把结果包装成绝对性能排名。

报告支持 JSON 和可读 HTML。报告可由已采集快照生成，并明确记录未能读取的字段和原因。导出前提供脱敏预览；默认不包含唯一设备标识。保存位置由用户选择。

## 11. 发行版与打包

优先支持 Debian/Ubuntu、Fedora、Arch Linux 和 openSUSE 系列，兼顾衍生发行版。首期发布策略优先发行版原生包，AppImage 作为补充分发形式。包应声明准确的 Qt、系统库和可选工具依赖；按发行版政策拆分可选后端，避免把单一传感器/桌面服务作为硬依赖。

构建和运行检查至少覆盖主流发行版当前受支持版本中的代表性环境、Wayland 与 X11（可用时）、有无可选工具及不同 GPU 渲染后端。UI 渲染失败时提供可理解的诊断和软件渲染回退。

## 12. 许可证与第三方软件

引入或调用第三方项目之前建立依赖清单，记录版本、许可证、链接方式、源码修改和分发义务。特别检查 GPL 系列工具（如 stress-ng、sysbench、glmark2/Phoronix Test Suite 等）与应用分发方式是否兼容；`libsensors` 等库的许可证与相应工具本身许可证需分别核查。通过运行外部可执行程序与链接其库的义务不同，不能仅凭项目名称推断。

优先使用系统提供的库和协议实现集成；不复制大段 GPL 代码到应用。发布前由项目维护者复核 SPDX 标识、NOTICE/第三方声明、源码提供义务和打包内容。许可证核验以选定版本的上游 LICENSE/COPYING 文件为准，本规格中的许可证示例不是最终法律结论。

## 13. 可观测性与故障处理

采集器对外提供结构化错误和能力状态；日志包含采集器、设备标识（必要时脱敏）、操作和失败原因，不默认记录敏感序列号。用户可查看诊断信息并复制报告。UI 应区分“没有该设备”“设备不暴露此指标”“权限不足”“读取失败”和“数据已过期”。单个采集器失败不得使其他硬件类别失效。

## 14. 分阶段交付

### 阶段 A：基础真实清单

C++/Qt/QML 框架、模块接口、普通用户权限模型、发行版/内核信息、CPU、内存、主板/BIOS、PCI/USB 和存储基础清单；建立真实机器诊断与采集状态展示。

### 阶段 B：实时传感器

hwmon/libsensors、CPU/GPU/存储可用指标、历史缓冲、筛选与图表；完善热插拔和缺失/权限状态。

### 阶段 C：系统与设备细节

显示器/EDID、网络、音频、电池、NVMe/SMART、NUMA 和更深入 GPU 适配器；按机器和发行版逐步扩充。

### 阶段 D：压力测试、基准和报告

引入受控的 stress-ng 工作流、首批基准适配、结果历史、报告导出、隐私控制和发行包。

各阶段按已验证能力开放功能。未实现或无硬件支持的字段不使用静态演示值填充。

## 15. 验收标准

1. 原生版展示的是本机真实数据；每项字段可追溯到来源、时间和状态，缺少权限/驱动/设备支持时能解释原因。
2. 在普通用户会话中可正常启动和使用基础信息功能；应用不要求 root，不因某个可选系统服务不存在而失败。
3. 至少覆盖 CPU、内存、主板/固件、PCI/USB、GPU/显示、存储、网络、音频/电池和系统信息的能力探测与清晰降级；具体字段按硬件可用性验收。
4. 传感器页面能持续更新、筛选和绘图，采集失败/设备移除后状态可恢复且不阻塞 UI。
5. 压力测试具备取消、超时、进程清理和结果状态；温度保护仅在对应传感器确实可读时标记为有效。
6. 基准结果包含可复现上下文；中止或失败不伪造成功结果。磁盘测试默认不写入用户设备。
7. 报告导出格式有效、脱敏默认生效，字段选择能控制导出范围。
8. 核心构建与测试覆盖至少 Debian/Ubuntu、Fedora、Arch、openSUSE 的代表性环境；可选能力缺失时有明确状态。
9. Qt Quick 实际渲染后端可诊断；常见硬件加速问题可回退到软件渲染。
10. 发布依赖经过版本和许可证核查，构建说明与可选运行时依赖完整。

## 16. 参考项目

本设计借鉴并计划持续核对以下上游项目和接口：

- 信息清单与设备：HWiNFO（功能参考）、AIDA64（信息深度参考）、hwinfo/libhd、Hardinfo2。
- 传感器与拓扑：s-tui（监控体验参考）、lm-sensors/libsensors、hwloc。
- Linux 系统接口：Linux `/proc` 与 sysfs 文档、udev/libudev、UDisks2/D-Bus、DRM/libdrm、libdisplay-info。
- 压力与基准：stress-ng、sysbench、fio、glmark2、Phoronix Test Suite、Google Benchmark。

参考项目用于理解能力、格式和成熟实现；具体集成前仍需按选定版本验证 API、发行版覆盖和许可证。
